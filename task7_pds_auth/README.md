# T07 Plan-Do-See 다이어리 2 · 회원 인증·인가와 세션 관리

T06 Plan-Do-See 다이어리에 회원가입·로그인·로그아웃, 세션 검증, 본인 기록만 보이는 접근 제어, 비밀번호 변경·계정 삭제, 5일 관찰 기록을 더한 정적 웹앱입니다. 서버는 Supabase(Auth + PostgreSQL)이고 빌드가 없습니다.

## 출발점(T06 이어받기)
- 브랜치 `t07-pds-auth`는 T06 제출 커밋 `1f9d33d`(Merge PR #5 `t06-pds-diary`)에서 시작합니다.
- 첫 커밋 `d3a1ae5`에서 `task6_pds_diary`를 이 폴더로 그대로 복사했고, 그 위에 인증 기능을 더했습니다.
- `task6_pds_diary` 폴더와 T06 DB 표(`public.pds_*`)는 바꾸지 않습니다. T07 기록은 새 표 `public.pds7_*`에 저장합니다.

## 화면과 요청 경로
화면은 `index.html` 한 장입니다.
- **로그인 전:** 로그인·가입 탭만 보입니다. 자료 요청은 보내지 않습니다.
- **로그인 후:** 계획·할 일·실행·회고(T06 기능), 5일 관찰, 도구 막대의 `내 계정`(비밀번호 변경·계정 삭제), 로그아웃이 보입니다. 선택한 계획은 주소의 `#plan=<id>`에만 남습니다. 토큰은 주소에 넣지 않습니다.
- **인증:** Supabase Auth `/auth/v1/*`(supabase-js 2.118.0, `vendor/supabase.js`에 고정해 자체 제공, PKCE).
  - 가입할 때는 이메일 확인이 필요합니다.
  - 확인 링크로 돌아온 주소의 코드는 바로 지웁니다.
- **자료:** `/rest/v1/rpc/pds7_*` 함수 17개만 씁니다. 브라우저가 쓰는 anon·authenticated 역할에는 표를 직접 읽거나 쓰는 권한을 주지 않습니다.
  - 계정: `pds7_me`(회원 등록·내 정보), `pds7_delete_account`
  - 계획: `pds7_create_plan`, `pds7_update_plan`, `pds7_delete_plan`
  - 할 일: `pds7_create_todo`, `pds7_get_todo`, `pds7_update_todo`, `pds7_complete_todo`, `pds7_reopen_todo`, `pds7_delete_todo`
  - 실행·회고: `pds7_add_execution`, `pds7_create_review`
  - 5일 관찰: `pds7_save_observation`, `pds7_save_daily_log`, `pds7_change_rule`
  - 전체 조회·내보내기: `pds7_snapshot`

## 인증·인가 요약
- **비밀번호:** 화면에서 입력한 비밀번호는 HTTPS로 Supabase Auth에 전달되고, Supabase Auth가 bcrypt(솔트 포함)로 저장합니다. 앱은 비밀번호를 자체 DB·로그·브라우저 저장소에 남기지 않고, DB 함수는 비밀번호 원문을 받지 않습니다.
- **세션 검증(모든 요청):** 액세스 토큰(JWT)의 서명·만료는 Data API가 확인합니다. 액세스 토큰 유효기간은 1시간이지만, 서버 세션은 그보다 오래 남고 리프레시 토큰으로 새 액세스 토큰을 받을 수 있습니다. DB 함수는 여기에 더해 두 가지를 확인합니다.
  - JWT의 `session_id`가 `auth.sessions`에 살아 있는지
  - 그 세션이 마지막 비밀번호 변경 뒤에 만들어졌는지

  하나라도 아니면 401입니다. 따라서 로그아웃하거나 비밀번호를 바꾸면, 앱을 거치지 않고 직접 API를 불러도 이전 토큰이 거절됩니다.
- **비밀번호 변경 감지:** `auth.users` 비밀번호 열이 바뀌면 트리거가 변경 시각을 기록합니다. 앱에서 바꾸든, 직접 Auth API로 바꾸든, 재설정 메일이나 관리자가 바꾸든 모두 기록됩니다.
  - 기록 대상은 T07 회원과, 이 스키마를 적용한 뒤 만든 모든 계정입니다. 회원 등록 전에 바꾼 경우도 포함합니다.
- **회원:** 자료 함수는 회원만 쓸 수 있습니다. 회원 등록 전이면 403입니다.
  - 회원 등록(`pds7_me`)도 위 세션 검증을 통과한 세션만 할 수 있습니다.
  - 이 앱을 적용하기 전부터 공유 프로젝트에 있던 계정은 회원 등록을 거절합니다(403, 새 이메일로 가입하라는 안내).
- **본인 기록만:** 모든 함수는 소유자를 확인합니다. 다른 계정의 ID를 넣으면 존재 여부를 드러내지 않고 404를 줍니다. 소유자 열은 바꿀 수 없습니다(트리거). 행 단위 보안(RLS)도 켜 두었습니다.
- **계정 삭제:** 다음이 모두 있어야 합니다. 삭제하면 로그인 정보·세션·T07 기록이 함께 지워집니다.
  - 회원 본인
  - 5분 안에 비밀번호로 다시 로그인한 세션
  - 확인 문구 `계정 삭제`

## 시험 (로컬 Supabase 스택)
Docker와 Supabase CLI 2.121.0이 필요합니다. 로컬 API 포트는 `supabase/config.toml` 기준 55421입니다.
```
cd task7_pds_auth
supabase start
docker exec -i supabase_db_task7_pds_auth psql -U postgres -d postgres -v ON_ERROR_STOP=1 < db/001_pds_schema.sql   # 로컬 DB에 T06 표 만들기
docker exec -i supabase_db_task7_pds_auth psql -U postgres -d postgres -v ON_ERROR_STOP=1 < db/101_pds7_auth_schema.sql
cd tests
npm ci
node make-test-users.mjs local   # 시험 계정 A·B·C, 비밀번호는 저장소 밖 파일에만
npm run test:auth      # 서버 인증·인가·세션 (node:test, HTTP)
npm run test:auth-ui   # 가입·확인 메일(Mailpit)·로그인·로그아웃·비밀번호 변경·계정 삭제·5일 관찰 화면 (Chrome)
npm run test:e2e       # T06 기능 회귀 (로그인 상태)
node --test migrate.test.mjs   # T06 기록 이관 SQL
```
- `test:auth`는 `T07_URL`·`T07_KEY`(공개 publishable key)를 주면 원격 프로젝트를 대상으로 HTTP 시험만 합니다. 관리자 SQL이 필요한 시험은 건너뜁니다.
- 시험 기록·화면 캡처는 저장소 밖에 저장합니다.

## 한계 (아직 막지 못한 것)
- **무차별 대입:** Supabase Auth 기본 속도 제한만 있습니다. 다단계 인증(MFA)은 없습니다. 유출 비밀번호 차단(leaked password protection)은 공유 프로젝트 설정에서 꺼져 있고, 이 과제에서 바꾸지 않았습니다.
- **토큰 저장 위치:** 토큰은 브라우저 localStorage에 저장됩니다. 화면에 스크립트가 주입(XSS)되면 토큰이 노출될 수 있습니다. 엄격한 CSP와 textContent 출력으로 줄였을 뿐입니다.
- **로그아웃 요청 실패:** 네트워크나 서버 오류로 로그아웃 요청이 실패하면 이 브라우저의 로그인 정보만 지워집니다. 서버 세션과 리프레시 토큰은 1시간이 지나도 저절로 끝나지 않습니다. 비밀번호를 바꿔야 끝납니다(서버가 변경 이전 세션을 모두 거절하고, 앱은 변경 뒤 모든 세션을 로그아웃합니다). 화면도 이렇게 안내합니다.
- **공유 로그인 계정:** 로그인 계정은 같은 Supabase 프로젝트의 다른 서비스와 같이 씁니다. 어느 앱에서 가입했는지는 서버가 증명할 수 없습니다. 계정을 삭제하면 같은 계정으로 쓰던 다른 서비스에도 로그인할 수 없습니다.
- **기존 공유 계정:** 이 앱을 적용하기 전부터 있던 공유 계정은 이 앱에서 쓸 수 없습니다. 새 이메일 계정이 필요합니다.
- **가입 확인 메일:** 공유 프로젝트는 Supabase 기본 메일 서버를 씁니다. 공식 문서(https://supabase.com/docs/guides/auth/auth-smtp)에 따르면 이 서버의 제한은 다음과 같습니다.
  - Supabase 프로젝트 팀에 등록된 주소로만 메일을 보냅니다. 다른 주소는 "Email address not authorized"로 거절됩니다.
  - 시간당 2통까지만 보냅니다.
  - 운영용이 아닙니다.

  그래서 지금은 아무 이메일로나 가입할 수 없습니다. 일반 외부 사용자의 가입은 별도 메일 서버(사용자 지정 SMTP)를 설정해야 가능합니다. 이 과제에서는 설정하지 않았고, 이메일 확인 끄기도 하지 않았습니다.
- **감사 로그:** 감사 로그는 없습니다.
- **T06 원본:** T06 원본 기록과 화면은 T06 방식(로그인 없음) 그대로 공개되어 있습니다.

## 아직 확인되지 않은 실제 사용 조건
- **공개 가입·확인 메일(C94·C95):** 원격에서는 사용자가 배포 주소에서 직접 가입해야 확인됩니다. 관리자가 만든 시험 계정으로는 판정하지 않습니다.
  - 배포 주소를 Auth Redirect URL 허용 목록에 넣어야 확인 메일 링크가 앱으로 돌아옵니다.
  - 기본 메일 서버 제한(팀 등록 주소만, 시간당 2통) 때문에, 확인 가능한 주소는 프로젝트 팀에 등록된 이메일입니다. 단, 이 앱 적용 전부터 있던 공유 계정의 이메일은 쓸 수 없습니다.
- **T06 기록 이관:** 사용자 가입 뒤 102를 한 번 실행해야 합니다.
- **5일 관찰:** 서로 다른 날짜 5일의 실제 기록과, 2일차 뒤 3일차 앞의 규칙 변경 1회는 사용자가 직접 남깁니다. 날짜는 서버(서울) 기준이고, 지난 날짜를 나중에 채울 수 없습니다.
