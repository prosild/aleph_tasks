01 · RESEARCH

로그의 발생 방식도
하나의 정보로 보기

Log-Entity Graph
시간 특성 확장

같은 로그가 나타나더라도 언제, 얼마나 집중해서, 어떤 중요도로 발생했는지에 따라 시스템 상태의 의미가 달라질 수 있다고 봤습니다.

기존 로그 이상탐지 모델은 로그 메시지의 내용이나 로그 사이의 관계를 학습하지만, 로그가 실제 운영 환경에서 발생하는 방식에 포함된 정보는 충분히 활용하지 못하는 부분이 있었습니다.

예를 들어 같은 종류의 로그라도 30분 동안 천천히 발생하는 경우와 수 초 안에 반복적으로 발생하는 경우는 동일한 상태라고 보기 어렵습니다. INFO와 ERROR 로그 역시 같은 의미를 갖지 않습니다.

시간 간격
가까운 시간에 발생한 로그의 관계를 더 강하게 반영하도록 연결 가중치를 조정했습니다.
Burst
짧은 시간 동안 로그가 집중적으로 발생하는 정도를 별도의 신호로 사용했습니다.
로그 레벨
INFO, WARN, ERROR 등의 중요도를 이용해 로그 사이의 관계를 동일하게 취급하지 않도록 구성했습니다.

이 특징들을 기존 Log-Entity Graph의 연결 관계와 가중치에 반영할 수 있도록 구조를 수정하고, 각 특징을 따로 적용했을 때와 여러 특징을 결합했을 때의 변화를 비교했습니다.

여기서 중요하게 본 것은 특정 데이터셋에서 가장 높은 점수를 얻는 설정보다 데이터가 달라져도 반복적으로 효과를 보이는 정보가 무엇인지 였습니다.

WHAT I FOUND

시간 정보를 반영했을 때 BGL, Thunderbird, HDFS 세 데이터셋에서 모두 F1이 개선됐습니다. 데이터별로 가장 효과적인 세부 방법은 달랐지만, 로그 사이의 시간적 관계는 서로 다른 환경에서도 반복적으로 효과가 나타나는 정보라는 점을 확인했습니다.

실험 결과에서 확인한 내용

특징을 각각 적용하고 결합하면서 데이터에 따라 나타나는 차이를 확인했습니다.

  • 시간 가중치는 세 데이터셋에서 공통적으로 F1 개선
  • Thunderbird에서는 로그 발생 집중도를 반영한 방식이 특히 높은 결과
  • HDFS에서는 일부 연결만 유지하는 Top-k 방식이 높은 결과
  • 여러 개선 방법을 결합한다고 해서 개별 적용보다 항상 성능이 좋아지지는 않음

02 · DEVELOPMENT

보이는 문제에서
실제 원인까지

웹 시스템
운영·유지보수

운영 시스템에서는 화면에 나타난 현상과 실제 문제가 발생한 위치가 항상 같지는 않았습니다.

웹 시스템 유지보수 업무에서 사용자 요청을 분석하고 화면과 서버의 처리 로직을 수정했으며, 필요한 데이터를 조회하고 처리하는 SQL도 함께 다뤘습니다.

특정 화면에서 값이 잘못 보이거나 요청한 기능이 예상대로 동작하지 않는 경우 화면 코드만 보고 수정하지 않았습니다. 사용자의 입력이 어떤 요청으로 전달되고, 서버에서 어떤 조건과 로직을 거쳐 어떤 데이터를 조회하는지 순서대로 확인했습니다.

운영 오류에서는 애플리케이션 로그를 통해 실제 요청이 어느 단계까지 정상적으로 처리됐는지 확인하고, 코드와 SQL, 데이터 상태를 함께 살피면서 원인의 범위를 좁혔습니다.

수정할 위치를 찾은 뒤에도 요청받은 화면이 정상적으로 보이는지만 확인하지 않았습니다. 변경한 로직이나 데이터를 함께 사용하는 기능을 찾아 기존 동작에 영향을 주는 부분이 없는지 확인했습니다.

WORKING APPROACH

사용자에게 보이는 결과를 출발점으로 삼되, 화면 → 서버 로직 → SQL → 데이터 → 로그 로 이어지는 처리 흐름 안에서 문제의 위치와 변경 범위를 판단하는 방식이 익숙해졌습니다.

Java 동아리
AI 교육과정

혼자 사용할 수 있는 것과 다른 사람이 이해할 수 있도록 설명하는 것은 다른 수준의 이해가 필요했습니다.

대학교 4학년 때 Java 프로그래밍을 어려워하는 학생들을 위해 학과에서 Java 동아리가 만들어졌고, 요청을 받아 다른 학생과 교대로 한 학기 동안 수업을 진행했습니다.

수업을 준비하면서 제가 이미 알고 있다고 생각했던 내용도 처음 배우는 사람이 따라올 수 있도록 다시 순서를 잡았습니다. 하나의 기능을 바로 보여주기보다 왜 필요한지를 설명하고, 작은 코드 단위로 동작을 확인한 뒤 다음 내용으로 이어지도록 구성했습니다.

설명만 듣고 끝나지 않도록 배운 내용을 직접 사용해 볼 수 있는 예제를 준비했고, 질문이 반복되는 부분은 설명 순서나 예시를 다시 정리했습니다. 수업 자료를 만드는 과정에서 제가 정확히 이해하지 못했던 부분도 다시 확인했습니다.

이후 AI 교육과정에서도 비슷한 방식으로 공부했습니다. 먼저 이해한 내용은 주변 교육생에게 설명했고, 코드 오류가 발생하면 완성된 답을 바로 알려주기보다 입력에서 결과가 나오는 과정 중 어느 지점에서 예상과 달라졌는지를 함께 확인했습니다.
